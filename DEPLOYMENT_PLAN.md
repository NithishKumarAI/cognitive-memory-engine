## Image and local staging verification

The frontend consumes `NEXT_PUBLIC_API_URL` at build time. Supply only the browser-reachable HTTPS **origin**, with no credentials/path/query/fragment; API, JWT and database keys remain backend secrets. Build rejects missing/loopback/insecure origins and unrecognized `NEXT_PUBLIC_*` settings. Docker has no localhost API default. A distinct `ALLOW_LOCAL_API_ORIGIN=1` build opt-in exists only for synthetic local tests; do not set it on a release image. Changing the URL at runtime cannot repair an already compiled browser bundle. HTTPS syntax validation does not prove DNS, reachability or CORS correctness.

When Docker Desktop is available, build frontend and backend with named local-test tags, without pushing. Use `docker build --build-arg NEXT_PUBLIC_API_URL=https://api.example.test -t cme-frontend-v1-test ./frontend` only for a non-routable build-policy check; a communication test must use a genuine local browser-reachable test API instead, explicitly opting into loopback. ## Resource and model gate

Both Docker runtimes use a non-root user. Frontend separates build/runtime dependencies and uses `npm ci`; backend installs pinned Python dependencies without a pip-version upgrade at image build. No image size or cold-start measurement is available. The current Linux Torch dependency markers include CUDA components, so do not claim the image is small or CPU-minimal. Do not silently replace Torch with another build or change the 768-dimensional model as part of deployment.

Embeddings lazily load `BAAI/bge-base-en-v1.5`; the new initialization lock prevents duplicate cold loads inside one process, not across workers/instances. `/health` verifies the database, not Gemini credentials, downloaded weights or model capacity. Provision a trusted, writable per-service `HF_HOME` cache (default `/home/app/.cache/huggingface` in the image), reviewed model assets/revision and appropriate egress. Do not mount an untrusted shared model cache. Measure fresh/warm memory, CPU, disk, load time and concurrent requests before selecting container memory/CPU, worker count, startup timeout and concurrency. Begin with conservative reviewed staging settings; fixed resource numbers without measurements are not readiness evidence.

## Required cloud controls before enabling AI

- Define explicit frontend/backend HTTPS origins, container ports, ingress identity/network access and least-privilege service identities. Keep the database on restricted networking. Configure exact `FRONTEND_ORIGINS`; do not use wildcard CORS as authorization.
- Supply `DATABASE_URL`, `SECRET_KEY`, `GEMINI_API_KEY`, model, timeout and token lifetime from a secret manager. Preserve the existing signing key/HS256 while changing JWT libraries so existing sessions remain valid. If key rotation is needed, schedule the reauthentication impact explicitly. No secret belongs in `NEXT_PUBLIC_*`, build arguments, image layers or logs.
- Start with `AI_ENABLED=false` and `REGISTRATION_ENABLED=false`. Registration closure does not stop login abuse. Local embeddings and their model downloads/CPU work remain available when Gemini is disabled. These switches are per-revision operational controls, not counters, instantaneous distributed revocation or a quota. Roll out the disabled revision and drain older enabled revisions when stopping traffic; in-flight work may complete.
- Put enforced gateway limits in front of register/login and AI routes, using IP plus verified identity as appropriate. Constrain raw JSON request sizes before parsing, keep audio at most 4 MiB and 120 seconds, and cap per-user/model-route rate and concurrent requests. Header values supplied by clients are not trusted user identities. Set provider-project request/token quota, monitored daily usage and an agreed spend ceiling/response. Merely saving `UsageLimit` rows does not enforce a budget.
- If introducing a distributed quota, design durable user/window records with atomic reserve/conditional increments, UTC window reset, a unique operation ID and safe concurrent handling. Reserve before dispatch; separately record successful work, failures and ambiguous timeouts. Do not assume a timeout was unbilled, refund ambiguous attempts or delete historical `usage_limits` rows. Review migrations and tests in a separate approved change; no billing system is implemented here.
- Set maximum instances and container concurrency with load evidence and database pool limits. Maximum instances constrain capacity, not the number of requests per user over time. See [Cloud Run maximum instances](https://docs.cloud.google.com/run/docs/configuring/max-instances). Configure alarms and an on-call shutdown action. Alerts-only budgets notify; do not treat them as enforced caps. Confirm which service-specific spend-cap mechanisms are supported and active rather than assuming an alert stops Gemini. See [Cloud Billing budgets](https://docs.cloud.google.com/billing/docs/how-to/budgets).
- Use redacted status/latency/usage telemetry. Exclude Authorization, passwords, reflections, audio and prompt/response bodies from logs. Set access, retention, deletion and backup policies; confirm provider data handling. No automated account-erasure/retention sweep is supplied by this application.
